# <img src="frontend/public/assets/favicon.svg" width="44" height="44" align="texttop" alt=""> 3S-UI
[English](README.md) · [Русский](README.ru.md)

3S-UI — открытая панель управления [sing-box](https://github.com/SagerNet/sing-box). Она даёт простой многоязычный интерфейс для развёртывания, настройки и мониторинга самых разных прокси- и VPN-протоколов — от одного VPS до конфигурации из нескольких узлов.

Фронтенд 3S-UI переписан целиком, а сверху добавлено множество возможностей, делающих работу с панелью удобнее.

## Возможности

- **Мультипротокольность** — VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC,
  AnyTLS и другие, на входящих и исходящих, плюс endpoints WireGuard, WARP и
  Tailscale ([полный список](#protocols)).
- **Входящие WireGuard и AmneziaWG** — серверы под управлением панели: peer на
  каждого клиента, конфиги, ссылки и QR, трафик идёт через правила sing-box
  ([подробности](#входящие-wireguard-и-amneziawg)).
- **qWDTT** — встроенный сервер туннеля через звонки VK с автогенерацией VK
  hash, маршрутизацией по правилам sing-box и ссылками `qwdtt://` в подписках
  ([подробнее](#qwdtt-туннель-через-звонки-vk)).
- **TLS в одном месте** — Reality, отпечатки uTLS, XTLS и сертификаты, которые
  регистрируются один раз, а затем выбираются для каждого входящего.
- **Правила маршрутизации** — совпадение по домену, IP, порту, протоколу,
  процессу, пользователю и rule-set, с объединением через and/or; у DNS свой
  отдельный список.
- **Управление клиентами** — квота трафика, срок действия, лимит IP, статус
  «онлайн» в реальном времени, а также ссылки для обмена, QR-коды и подписки в
  одно нажатие.
- **Статистика трафика** — по входящим, по клиентам и по исходящим, с
  управлением сбросом.
- **Подписки** — форматы `link`, `json` и `clash`, расход и срок действия
  возвращаются в клиентское приложение, внешние ссылки включаются в общую выдачу.
- **Кластер из нескольких узлов** — мониторинг состояния узлов, общие
  пользователи между ними и объединение их серверов в одну подписку
  ([подробнее](#кластер-из-нескольких-узлов)).
- **Автоматический HTTPS** — выпуск и продление сертификатов Let's Encrypt, плюс
  автоматический обратный прокси nginx ([подробнее](#домены-и-сертификаты)).
- **Уведомления** — события узлов, ядра, исходящих, клиентов, ресурсов и входа
  отправляются в Telegram, на webhook или по e-mail, плюс Telegram-бот для управления
  панелью с телефона ([подробнее](#уведомления-и-telegram-бот)).
- **Защита входа** — ограничение частоты неудачных попыток с сохранением в базе,
  двухфакторная аутентификация TOTP и сброс всех сессий при смене учётных данных
  ([подробнее](#защита-входа)).
- **Обновление в одно нажатие** — прямо из панели, с проверкой контрольных сумм.
- **Переписанный интерфейс** — фронтенд с нуля, собственные компоненты, тёмная и
  светлая темы, шесть языков (включая RTL).

<details id="protocols">
  <summary>Поддерживаемые протоколы</summary>

- Общие: Mixed, SOCKS, HTTP/HTTPS, Direct, Tun, Redirect, TProxy
- На основе V2Ray: VLESS, VMess, Trojan, Shadowsocks (в т. ч. `plugin` / `plugin_opts`)
- Другие протоколы: ShadowTLS, Hysteria, Hysteria2, Naive¹, TUIC, AnyTLS, Snell²
- Только входящие: Cloudflared
- Только исходящие: Tor, SSH, Bridge, Selector, URLTest
- Endpoints: WireGuard, WARP, Tailscale, OpenConnect, OpenVPN — с проверкой задержки для отдельного endpoint или для всех сразу
- Поддерживается XTLS, а в форме исходящего доступен Hysteria port hopping

<sup>1</sup> Naive требует тулчейн cronet, который собирается не везде: официальные сборки для
Linux включают его только на amd64, arm64, armv7 и 386. На armv6, armv5 и s390x исходящее
соединение Naive сообщит, что бинарник собран без него.

<sup>2</sup> Входящий Snell в sing-box говорит на v5 и v6, а исходящий — на v4 и v6, поэтому
клиентская конфигурация генерируется только для слушателя v6; слушатель v5 рассчитан на
клиентов, настраиваемых вручную (Surge).

</details>

## Установка

### Linux/macOS

```sh
bash <(curl -Ls https://raw.githubusercontent.com/samur005/3s-ui/main/install.sh)
```

Язык следует `$LANG`, либо укажите `en`, `fa`, `ru`, `vi`, `zhcn` или
`zhtw`:

```sh
S3UI_LANG=ru bash <(curl -Ls https://raw.githubusercontent.com/samur005/3s-ui/main/install.sh)
```

### Alpine Linux

В Alpine нет ни `bash`, ни `curl` — доставьте их, после чего установщик сам
определит Alpine и поставит панель как службу OpenRC:

```sh
apk add bash curl
bash <(curl -Ls https://raw.githubusercontent.com/samur005/3s-ui/main/install.sh)
```

### Windows

1. Скачайте последний релиз для Windows с [GitHub Releases](https://github.com/samur005/3s-ui/releases/latest)
2. Распакуйте ZIP-файл
3. Запустите `install-windows.bat` от имени администратора
4. Следуйте указаниям мастера установки
5. Откройте панель по адресу http://localhost:2095/app

### Docker

```shell
mkdir 3s-ui && cd 3s-ui
wget -q https://raw.githubusercontent.com/samur005/3s-ui/main/docker-compose.yml
docker compose up -d
```

### Обновление

Новые релизы отмечаются на плашке версии в боковой панели — проверку выполняет
браузер, поэтому самому серверу с панелью доступ к GitHub не нужен. На Linux
(systemd или Docker) обновление выполняется в одно нажатие: панель скачивает
релиз, сверяет его с опубликованным `SHA256SUMS`, пробно запускает новый
бинарник, затем заменяет его и перезапускается. Без SSH.

> В Windows работающий `.exe` не может заменить сам себя, поэтому плашка версии
> лишь ведёт на страницу релиза. В Docker новый бинарник живёт в записываемом слое
> контейнера: он переживает `docker restart`, но пересоздание контейнера вернёт
> версию из образа — чтобы обновление закрепилось, скачайте новый образ.

## Кластер из нескольких узлов

Одна панель может управлять остальными. Добавьте удалённый экземпляр 3S-UI на
странице **Узлы** (Nodes), указав его адрес и API-токен, и главная панель будет:

- **Следить за ним** — heartbeat раз в 5 секунд сообщает по каждому узлу: в сети,
  не в сети или ядро остановлено (панель доступна, но sing-box не работает).
- **Делить с ним пользователей** — клиенты главной панели, ссылающиеся на входящие
  узла, отправляются на этот узел и поддерживаются в синхронном состоянии, а трафик
  каждого узла сворачивается обратно в счётчики главной панели. Синхронизация
  ограничена группой `@cluster`, поэтому собственных локальных пользователей узла она
  не трогает.
- **Собирать его серверы в одну подписку** — одна ссылка подписки содержит и серверы
  главной панели, и серверы всех привязанных узлов.

Узел — это просто другой экземпляр 3S-UI, работающий через API v2 (заголовок `Token`):
никакого агента ставить не нужно, а единственная настройка на стороне узла — создать
этот API-токен в его собственной панели, так что уже существующие панели можно принять
как есть. Входящие, принятые с узла, становятся на главной панели репликами только для
чтения — редактируйте их на том узле, которому они принадлежат.

<details>
  <summary>Управление синхронизацией узлов через API</summary>

`POST <путь панели>apiv2/save` (по умолчанию путь панели — `/app/`, то есть
`/app/apiv2/save`) запускает немедленную рассылку по узлам, как в веб-интерфейсе,
только если в запросе передан `sync=true`; без него изменения клиентов и входящих
всё равно сойдутся благодаря ежечасной сверке.

Ответ `save` описывает, что именно было записано, а не новое состояние
панели: в нём есть `object`, `action` и id затронутых строк, а при `object`
равном `clients` и одиночном действии `new` или `edit` — ещё и полные строки
клиентов (вместе со сгенерированными `links`). Остальное читайте через
эндпоинты чтения, например `apiv2/clients`.

</details>

## Домены и сертификаты

Всё, что касается TLS, живёт на вкладке **Домены и сертификаты** в настройках панели.
Панель и сервис подписок выбирают каждый свой домен, а пути к сертификатам следуют за
выбранным доменом — переносить пути к файлам вручную больше не нужно.

**🔐 Автоматические сертификаты (ACME / Let's Encrypt) — рекомендуется.** Введите
домен, укажите e-mail и нажмите «выпустить»: 3S-UI получит и будет автоматически
продлевать бесплатный сертификат Let's Encrypt, после чего панель будет доступна по
адресу `https://<your-domain>:2095/app`. Требуется, чтобы TCP-порт **80** был доступен
из интернета (HTTP-01 challenge). ACME работает только на Linux и скрыт в Windows.

<details>
  <summary>Как проходит выпуск и что учесть с портом 80 в Docker</summary>

Выпуск выполняется через **acme.sh** — при первом использовании панель сама установит
acme.sh (а также `socat`, необходимый для standalone-проверки) и включит автопродление
через собственную cron-задачу acme.sh, так что вам не нужно ничего настраивать в
планировщике.

Способ проверки по умолчанию — **auto**: standalone, если порт 80 свободен, иначе
задействуется уже работающий nginx, и при необходимости под `/etc/nginx/conf.d`
создаётся минимальный блок `server_name`. Можно явно выбрать **standalone** или
**nginx**, если хотите решать сами. При продлении сертификат перечитывается на лету —
перезапуск не нужен.

> Чтобы опубликовать порт 80 в Docker: раскомментируйте строку `80:80` в
> `docker-compose.yml` или добавьте `-p 80:80` в `docker run`. Сертификаты хранятся в
> `/root/cert/<домен>/` под именами `fullchain.pem` / `privkey.pem` и сохраняются при
> перезапусках (том в команде Docker выше как раз монтирует этот путь). Если домен/порт
> настроены неправильно, 3S-UI переключается на HTTP.

</details>

<details>
  <summary>Собственный сертификат</summary>

Сертификаты, которыми вы управляете сами — Cloudflare origin CA, корпоративный CA,
результат работы certbot — регистрируются на той же вкладке. 3S-UI проверяет, что файлы
читаются, что ключ соответствует сертификату и что сертификат действительно покрывает
домен; после этого домен становится доступен для выбора на вкладках «Интерфейс» и
«Подписка», как любой другой. Зарегистрированные сертификаты попадают в резервные копии
базы данных.

Чтобы выпустить сертификат самостоятельно через Certbot:

```bash
snap install core; snap refresh core
snap install --classic certbot
ln -s /snap/bin/certbot /usr/bin/certbot

certbot certonly --standalone --register-unsafely-without-email --non-interactive --agree-tos -d <Your Domain Name>
```

Затем зарегистрируйте полученные `fullchain.pem` / `privkey.pem` на вкладке
**Домены и сертификаты**.

</details>

<details>
  <summary>За обратным прокси</summary>

Включите **TLS терминируется обратным прокси**, и 3S-UI сам напишет vhost:
`/etc/nginx/conf.d/3s-ui-proxy-<домен>.conf`, направленный на панель и с нужными
заголовками проксирования, проверит его через `nginx -t`, перезагрузит nginx и откатит
изменения, вернув собственное сообщение об ошибке nginx, если что-то не получится.
Сервер подписок может стоять за тем же прокси.

</details>

## Уведомления и Telegram-бот

Всё находится на вкладке **Уведомления** в настройках панели. Включите их, выберите
события и укажите хотя бы один канал:

- **Telegram** — токен бота и один или несколько chat ID, при желании через прокси или
  собственный Bot API-сервер.
- **Webhook** — каждое событие доставляется на ваш URL.
- **E-mail** — обычный SMTP.

У каждого канала своя очередь, поэтому зависший канал не задерживает остальные. События:
узел или ядро sing-box упало или поднялось, исходящее не прошло проверку по URL, у клиента
закончился трафик или подходит срок, CPU или память выше порога, а также вход — успешный,
неудачный и заблокированный. Пороги и число неудачных проверок, после которого узел
считается упавшим, — настройки на той же вкладке; повторяющееся состояние сообщается
один раз и затем не повторяется 24 часа. Отчёт по расписанию (cron или `@daily`)
подводит итог по панели, при желании с приложенной резервной копией базы.

**Telegram-бот** на той же вкладке превращает эти chat ID в чаты администраторов, из
которых панелью управляют с телефона: `/status`, `/nodes`, `/clients` (близкие к лимиту,
или `/clients <имя>` для поиска), `/online`, `/traffic` за последние 24 часа, `/inbounds`,
`/bans` и `/backup`. Из карточки клиента оператор может отправить подписку или ссылку на
отдельный входящий — текстом и QR-кодом — и привязать клиента к аккаунту Telegram, выбрав
контакт. Привязанный клиент затем может спросить у бота свои расход и ссылки на своём
языке, а когда подписка заканчивается, получает уведомление напрямую — не то, что видит
оператор, и без имени хоста панели. Все остальные получают `/id` (свой Telegram ID, чтобы
оператор мог привязать) и ничего, что выдавало бы, какая панель стоит за ботом.

## Защита входа

Вход защищают три механизма, все включены по умолчанию:

- **Ограничение частоты** — пять неудач за пять минут блокируют идентичность на
  пятнадцать; считается и по IP источника, и по имени пользователя, так что смена любого
  из них не даёт нового лимита. Состояние хранится в базе, и перезапуск блокировку не
  снимает. Три числа находятся на вкладке **Интерфейс** в настройках панели; `0` в любом
  из них отключает механизм. За обратным прокси панель берёт адрес клиента из
  `X-Forwarded-For` только при включённом режиме обратного прокси — иначе все попытки
  засчитывались бы прокси и делили один лимит.
- **Двухфакторная аутентификация** — TOTP, совместима с любым приложением-аутентификатором.
  Включается по значку щита на странице **Администраторы**. Секрет сохраняется только
  после того, как проверен код из него, поэтому брошенная привязка не оставит вас снаружи;
  если утерян сам аутентификатор, `3sui admin -disable-2fa` на хосте его отключит.
- **Сброс сессий** — смена пароля или имени пользователя отзывает все выданные до этого
  сессии, включая открытые WebSocket-соединения.

## qWDTT (туннель через звонки VK)

3S-UI умеет сам запускать сервер [qWDTT](https://github.com/SpaceNeuroX/proxy-turn-vk-android):
клиенты подключаются через TURN-релеи звонка VK, а hash этого звонка панель
создаёт и поддерживает сама. Отдельная панель wdtt не нужна. Добавьте входящее типа **qwdtt** на странице
**Входящие** (рядом с VLESS и остальными): настройки, переключатель и клиенты
находятся там. Страница **qWDTT** в боковом меню хранит cookies VK, работу с
hash, ссылку и журнал. Настройки qWDTT от v2.2.0 при первом запуске сами
превращаются в это входящее (все, у кого была ссылка, привязываются к нему).
Поддерживается одно входящее qWDTT; sing-box его не видит.

- **Сервер** — панель следит за sidecar `qwdtt` (запуск, остановка, перезапуск
  при смене настроек, пауза между падениями, журнал). Настройки хранятся в базе
  панели (`qwdtt_states`), поэтому входят в резервные копии. Только Linux; в
  других системах страница сообщает об этом и ничего не запускается.
- **Маршрутизация** — при включённом *Через sing-box* (по умолчанию) панель
  добавляет в ядро скрытый TUN-inbound (`qwdtt-tun`, интерфейс `qwdtt0`) и
  направляет в него интерфейсы сервера `wdtt0` / `wdttraw0` через policy routing
  (`ip rule … lookup 1977`), поэтому ваши правила и outbound'ы действуют и на
  клиентов qWDTT. Необязательный *Outbound* отправляет весь их трафик в один
  тег. Если выключить, сервер делает NAT напрямую в интернет.
- **VK hash** — в поле *Cookies VK* вставляются cookies аккаунта VK (JSON-массив
  `{name, value}` из экспорта браузера или заголовок `Cookie:`; обязателен
  `remixsid`). Они хранятся в базе и в браузер не возвращаются. *Создать hash*
  запускает звонок от этого аккаунта и сохраняет его join hash. При включённых
  *Автоматических hash* панель создаёт hash, если его нет, и каждые 5 минут
  проверяет через `calls.getCallPreview`, жив ли каждый hash; после двух
  «мёртвых» ответов подряд заменяет его. Переменная `S3UI_VK_HASH` (через
  запятую, до 4) задаёт hash из окружения: она приоритетнее сохранённых и
  отключает генерацию.
- **Подписки** — клиенты, привязанные к входящему qWDTT (при создании или на
  странице клиента), получают в подписке одну строку `qwdtt://config?…`. Ссылка собирается на
  лету, поэтому новый hash сразу попадает во все подписки. На странице есть QR и
  JSON-вариант.
- **Файрвол** — откройте порт DTLS (`56000/udp` по умолчанию) и, если нужен,
  raw-IP порт (`56003/udp`).
- **Требуется** root (или `CAP_NET_ADMIN`), `ip` (iproute2) для маршрутизации и
  `iptables` либо `nft` для собственного NAT сервера.

### Бинарник qwdtt

Sidecar — это команда `server` из SpaceNeuroX/proxy-turn-vk-android v1.4.4
(закреплённый коммит) с патчем `scripts/patches/qwdtt-subnet.patch`, который
переносит подсеть туннеля в 10.68.0.0/16, чтобы он уживался рядом с wdtt.
Собирает его `scripts/build-qwdtt.sh` (чистый Go, любые `GOOS/GOARCH/GOARM`);
версия закреплена только в этом скрипте:

- **install.sh / релизный архив** — workflow собирает его под каждую
  архитектуру в `3s-ui/qwdtt`; файл попадает в `/usr/local/3s-ui/qwdtt`, а
  самообновление панели обновляет и его.
- **Docker** — оба Dockerfile собирают его в `/app/qwdtt`. Для qWDTT в
  контейнере нужны `network_mode: host` и `cap_add: [NET_ADMIN]` (см.
  комментарии в `docker-compose.yml`).
- **Из исходников** — `scripts/build-qwdtt.sh /usr/local/3s-ui/qwdtt`.
- **Свой бинарник** — укажите путь в `S3UI_QWDTT_BIN`. Порядок поиска: эта
  переменная, `<каталог панели>/bin/qwdtt`, `<каталог панели>/qwdtt`, затем `PATH`.

Чтобы обновить qWDTT, поменяйте `QWDTT_REF` в `scripts/build-qwdtt.sh` (патч
пересоздайте, если он не применяется), пересоберите и перезапустите сервер на
странице. Учёт трафика по клиентам из других панелей qWDTT не реализован.

## Входящие WireGuard и AmneziaWG

Добавьте на странице **Входящие** входящее типа **wg** (WireGuard) или **awg**
(AmneziaWG). В списке типов они в отдельной группе «Запускает панель», а на
карточке указано, какой движок их запускает. Можно создать несколько штук каждого
вида: у каждого свой UDP-порт, подсеть туннеля и интерфейс.

- **Движок** — один userspace-движок (amneziawg-go) для обоих: `awg` без
  маскировки — это обычный WireGuard. Только Linux; панель сама создаёт
  интерфейс (`s3wg<id>` / `s3awg<id>`), ключи и peers.
- **Клиенты** — привяжите клиентов ко входящему (при создании или в форме
  клиента). Каждый получает peer со своими ключами, preshared-ключом и адресом
  из подсети (первый адрес занимает сервер). Отвязка сохраняет peer, повторная
  привязка вернёт тот же конфиг; удаление клиента удаляет peer. Правка входящего
  ключи не меняет.
- **Как получить конфиг** — кнопка **QR** у клиента, вкладка *WG / AWG*: QR,
  *Копировать конфиг*, *Скачать .conf* и для AmneziaWG ключ `vpn://` приложения
  Amnezia. В подписке со ссылками для каждого входящего есть строка
  `wireguard://` (WireGuard) или `vpn://` (AmneziaWG), а
  `<адрес подписки>/<клиент>?format=conf[&inbound=<id>]` отдаёт файл `.conf`
  (формат wg-quick / awg-quick).
- **Версии AmneziaWG** — 1.0, 1.5, 2.0, 2.5, 3.0 и 3.1. Форма показывает только
  параметры выбранной версии: Jc/Jmin/Jmax, S1/S2 и H1–H4 — у всех; цепочки
  I1–I5 — с 1.5; S3/S4 и диапазоны H — с 2.0; с 3.0 защита заголовков, паддинг
  и таймеры (S1–S4 не меньше 12, H снова одиночные числа); 3.1 добавляет
  случайные хвосты и отключение cookies. Значения создаются случайно и
  проверяются (пересекающиеся диапазоны H, S2 = S1 + 56 и подобное отклоняются).
  Отдельной спецификации 2.5 нет, поэтому у неё параметры версии 2.0. У клиентов
  должен быть тот же набор; смена версии пересоздаёт интерфейс, peers остаются.
- **Маршрутизация** — с опцией *Через sing-box* (по умолчанию) панель добавляет
  в ядро скрытый TUN-входящий (`wgtun-<id>`, интерфейс `s3c<id>`) и направляет
  в него трафик интерфейса политикой маршрутизации, поэтому действуют ваши
  правила и исходящие; можно принудительно выбрать один исходящий. Сохранение
  входящего, которому нужен TUN, один раз перезапускает ядро. Если выключить,
  сервер делает NAT в интернет через iptables.
- **Файрвол** — откройте UDP-порт каждого входящего (51820 у первого, дальше
  следующие свободные) в файрволе хоста; панель этого не делает.
- **Нужны** root (или `CAP_NET_ADMIN`), `/dev/net/tun` и `ip` (iproute2);
  `iptables` — для режима NAT и правил `FORWARD`. В Docker — `network_mode: host`
  и `cap_add: [NET_ADMIN]`, как для qWDTT.
- **Не сделано** — счётчики трафика по клиентам, IPv6 внутри туннеля (AllowedIPs
  `::/0` по умолчанию отправляет IPv6 клиентов в туннель, где он отбрасывается,
  утечки нет) и хосты только с nftables.

## Xray-core (второе ядро)

3S-UI умеет запускать официальный [Xray-core](https://github.com/XTLS/Xray-core)
рядом с sing-box. Добавьте входящее типа **xvless** (группа *Xray* в выборе
типа). В списке входящих можно фильтровать по движку (sing-box / Xray / сервис
панели), на карточке указан движок.

- **Закреплённый релиз** — `v26.11.9` (`xray/version.go`, `scripts/fetch-xray.sh`).
  Бинарник лежит в релизном архиве и Docker-образе рядом с панелью; можно
  задать `S3UI_XRAY_BIN`.
- **Транспорты VLESS** (официальный `streamSettings.method`): raw (TCP), xhttp,
  mkcp, grpc, websocket, httpupgrade. REALITY только с raw, xhttp или grpc.
  У mKCP больше нет header/seed — используйте FinalMask (например salamander).
- **Защита** — none, tls (файлы сертификата на хосте), reality (ключи x25519).
- **Vision** — `xtls-rprx-vision` только с raw+tls/reality или с VLESS Encryption.
- **VLESS Encryption** — опциональная пара ML-KEM-768 из `xray vlessenc`
  (кнопка «Создать пару»). `decryption=none` отключает.
- **Клиенты** — привязка как обычно; в подписке и QR — ссылки `vless://…`.
  Используется UUID из блоков `xvless`/`vless` клиента.
- **Через sing-box (по умолчанию)** — расшифрованный TCP+UDP уходит в loopback
  mixed-входящий с тем же тегом, что у строки, поэтому действуют правила и
  исходящие панели. Можно закрепить исходящий. Выключено — `freedom` в Xray
  (без правил панели). Имя клиента VLESS передаётся как SOCKS-логин (`auth_user`). Исходный IP **не** сохраняется (loopback).
- **Не сделано** — перевод правил панели в JSON Xray, reverse portal/bridge,
  другие протоколы Xray кроме VLESS, счётчики трафика для xvless.

AmneziaWG **2.5** использует тот же набор параметров, что и 2.0: отдельной
официальной спецификации 2.5 для этой панели не подтверждено.

  <summary>Сборка и запуск из исходников</summary>

```shell
./run3sui.sh
```

`build.sh` собирает фронтенд, копирует его в `web/html/` для `//go:embed` и собирает
бинарник с нужными build tags; `run3sui.sh` поверх этого сразу его запускает. Ручная
сборка требует тех же тегов — см. [CONTRIBUTING.md](CONTRIBUTING.md).

</details>
